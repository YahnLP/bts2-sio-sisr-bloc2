## Partie A – Mesurer l'état de référence (≈ 20 min)

**But :** connaître le comportement du lien **avant** toute modification.

Sur **CLI** : `iperf3 -s`. Sur **SRV** :

```bash
ping -c 20 192.168.60.20
iperf3 -c 192.168.60.20 -t 15
```

Relève :

| Mesure | Valeur de référence |
|---|---|
| RTT moyen (ligne `rtt min/avg/max/mdev`) | |
| Écart-type du RTT (`mdev`, indicateur de gigue) | |
| Débit maximal (iperf3, Mbit/s) | |

**J'anticipe.** Pourquoi le débit mesuré entre deux machines virtuelles n'est-il pas celui d'un vrai lien Internet ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Le réseau interne de VirtualBox est **logiciel** : il n'a pas de limitation physique et son débit dépend de la machine hôte (souvent plusieurs centaines de Mbit/s à plusieurs Gbit/s). C'est pourquoi on **crée artificiellement un goulot** à la partie B.

</details>

## Partie B – Créer un goulot et constater la dégradation (≈ 35 min)

**But :** limiter la **sortie de SRV** à 10 Mbit/s, sans priorité, et observer l'effet d'un transfert sur la latence.

Sur **SRV** :

```bash
sudo tc qdisc add dev $IF root handle 1: htb default 10
sudo tc class add dev $IF parent 1: classid 1:10 htb rate 10mbit
tc qdisc show dev $IF
tc class show dev $IF
```

**Je comprends.** `htb default 10` : que signifie le « 10 » ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Tout paquet qui ne correspond à aucun filtre est envoyé dans la **classe 1:10** (la classe « par défaut »). Ici, toute la sortie passe donc par une seule classe limitée à 10 Mbit/s.

</details>

Lance dans **deux terminaux** de SRV, **en même temps** :

```bash
iperf3 -c 192.168.60.20 -t 30        # terminal 1 : transfert massif
ping -c 25 192.168.60.20             # terminal 2 : mesure du délai pendant le transfert
```

| Mesure | Référence (A) | Avec goulot et transfert (B) |
|---|---|---|
| Débit iperf3 | | |
| RTT moyen | | |
| Écart-type du RTT | | |

**J'anticipe.** Avant de lancer : que va-t-il arriver au RTT du `ping` pendant le transfert ? Pourquoi ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Le **débit** se stabilise autour de **10 Mbit/s**. Le **RTT augmente nettement** (de l'ordre de plusieurs dizaines à plusieurs centaines de millisecondes selon la taille de la file) et la **gigue** aussi : les paquets du `ping` **attendent derrière** ceux du transfert dans la file de la classe unique. C'est la **latence d'attente en file**.

</details>

**Point de contrôle :** capture d'écran de la sortie de `ping` pendant le transfert.

## Partie C – Prioriser le trafic sensible (≈ 40 min)

**But :** donner la priorité aux paquets ICMP (le `ping` joue le rôle d'un flux sensible au délai).

Supprime la configuration précédente, puis crée **deux classes** :

```bash
sudo tc qdisc del dev $IF root
sudo tc qdisc add dev $IF root handle 1: htb default 20
sudo tc class add dev $IF parent 1: classid 1:1 htb rate 10mbit
sudo tc class add dev $IF parent 1:1 classid 1:10 htb rate 2mbit ceil 10mbit prio 0
sudo tc class add dev $IF parent 1:1 classid 1:20 htb rate 8mbit ceil 10mbit prio 1
sudo tc filter add dev $IF protocol ip parent 1:0 prio 1 u32 match ip protocol 1 0xff flowid 1:10
```

| Élément | Rôle |
|---|---|
| Classe `1:1` | Le lien total, limité à 10 Mbit/s |
| Classe `1:10` | Flux **prioritaire** : 2 Mbit/s garantis, jusqu'à 10 si le lien est libre, priorité `0` (la plus haute) |
| Classe `1:20` | Flux **ordinaires** : 8 Mbit/s garantis, priorité `1` |
| Filtre | `ip protocol 1` = ICMP → classe `1:10` |

**Je comprends.** Pourquoi la classe prioritaire n'a-t-elle que 2 Mbit/s garantis alors qu'elle ne porte que des `ping` ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Un flux prioritaire doit être **plafonné** et dimensionné sur son besoin réel : sinon il pourrait **monopoliser** le lien et affamer les autres flux (c'est le principe de la LLQ). La garantie n'est pas un maximum : `ceil 10mbit` lui permet d'utiliser le reste s'il est libre.

</details>

Relance **les deux mesures simultanées** (iperf3 de 30 s et ping), puis note les résultats :

| Mesure | Référence (A) | Goulot sans priorité (B) | Avec priorisation (C) |
|---|---|---|---|
| Débit iperf3 | | | |
| RTT moyen | | | |
| Écart-type du RTT | | | |

Observe aussi les compteurs par classe :

```bash
tc -s class show dev $IF
```

**Je comprends.** Que montrent les compteurs ? Quelle classe a transporté le plus d'octets, et pourquoi ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

La classe **1:20** porte presque tous les octets (le transfert iperf3) ; la classe **1:10** n'en porte que très peu (les `ping`). Le RTT du `ping` est revenu **proche de la référence** parce que ses paquets ne passent **plus derrière** ceux du transfert. Le débit d'iperf3 reste proche de 8 à 10 Mbit/s : la priorisation **n'a pas créé de bande passante**, elle a **réparti** la file.

</details>

**Point de contrôle :** le tableau complété à trois colonnes et une capture de `tc -s class show`.

## Partie D – Observer un marquage DSCP (≈ 25 min)

**But :** voir qu'un paquet peut porter sa priorité dans son en-tête.

Sur **CLI** (dans un terminal) : `sudo tcpdump -n -v -i $IF icmp`

Sur **SRV** : `ping -c 3 -Q 0xb8 192.168.60.20`

L'option `-Q 0xb8` fixe le champ « type de service » de l'en-tête IP.

**J'anticipe.** `0xb8` en décimal vaut 184. Quelle valeur de DSCP obtient-on en retirant les deux derniers bits (184 ÷ 4) ? ______

<details markdown="1">
<summary>Éléments de réponse</summary>

184 ÷ 4 = **46**, soit **DSCP EF** (*expedited forwarding*), la valeur usuelle de la **voix**. Dans la capture, tcpdump affiche `tos 0xb8` dans l'en-tête IP des requêtes.

</details>

**Je comprends.** Pourquoi un marquage posé par un poste utilisateur ne doit-il pas être cru aveuglément ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

N'importe quel utilisateur peut marquer ses paquets « prioritaires » pour s'octroyer de la bande passante. On **marque** ou on **re-marque** donc à la **frontière de confiance**, sur un équipement administré.

</details>

- lui réserve **128 kbit/s en priorité** ;
- partage équitablement le reste du trafic ;
- applique la politique **en sortie** de l'interface `serial 0/0/0`.


<details markdown="1">
<summary>Éléments de réponse</summary>

```text
class-map match-any VOIX
 match dscp ef
policy-map QOS-WAN
 class VOIX
  priority 128
 class class-default
  fair-queue
interface serial 0/0/0

```

## Partie A – Préparer le modèle et cloner (≈ 35 min)

**1.** Dans ta VM Debian de référence (appelons-la `modele`) : mise à jour, puis suppression de ce qui est propre à la machine.

```bash
sudo apt update && sudo apt -y upgrade
sudo rm -f /etc/ssh/ssh_host_*
sudo truncate -s 0 /etc/machine-id
sudo poweroff
```

**J'anticipe.** Pourquoi supprimer les clés `ssh_host_*` avant de cloner ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Ces clés sont l'**identité SSH** de la machine. Si on clone sans les supprimer, toutes les copies auraient les **mêmes clés** : un client ne pourrait plus distinguer les machines et l'authentification du serveur perdrait son sens. Elles seront **régénérées** au premier démarrage (voir la remarque ci-dessous).

</details>

> [!NOTE]
> Sur Debian, les clés d'hôte ne sont pas recréées automatiquement au démarrage si le paquet est déjà configuré. Sur chaque clone, lance une fois : `sudo dpkg-reconfigure openssh-server` (génère de nouvelles clés et relance SSH).

**2.** Sur l'hôte, crée un **clone complet** de `modele` pour chaque machine, avec un nouvel identifiant MAC.

```bash
for m in RTR VM-A VM-B; do
  VBoxManage clonevm modele --name "$m" --register --mode machine
done
VBoxManage list vms
```

**Point de contrôle :** `list vms` montre `RTR`, `VM-A`, `VM-B`.

**Je comprends.** Quelle différence y a-t-il entre un clone complet et un clone lié ? Pourquoi le choix d'un clone complet est-il plus sûr pour un laboratoire durable ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Un **clone complet** copie le disque : la VM est **indépendante**. Un **clone lié** ne stocke que les différences et **dépend** du disque d'origine : si celui-ci est supprimé ou déplacé, tous les clones sont perdus. Le clone lié économise de la place mais crée une dépendance.

</details>

## Partie B – Câbler les réseaux virtuels (≈ 40 min)

**1.** Configure les cartes depuis l'hôte (les VM étant éteintes).

```bash
VBoxManage modifyvm RTR  --nic1 intnet --intnet1 lab-a --nic2 intnet --intnet2 lab-b
VBoxManage modifyvm VM-A --nic1 intnet --intnet1 lab-a
VBoxManage modifyvm VM-B --nic1 intnet --intnet1 lab-b
```

**2.** Démarre les trois machines (`VBoxManage startvm RTR --type headless`, etc.) et configure les adresses. Relève d'abord les noms d'interface avec `ip -br a` (ils peuvent différer de `enp0s3`).

Sur **RTR** (`/etc/network/interfaces.d/lab`, adapte les noms) :

```text
auto enp0s3
iface enp0s3 inet static
    address 192.168.10.1/24

auto enp0s8
iface enp0s8 inet static
    address 192.168.20.1/24
```

Sur **VM-A** et **VM-B**, un fichier du même type avec l'adresse et la passerelle du plan visé.

Applique : `sudo systemctl restart networking` (ou redémarre la VM).

**3.** Active le routage sur **RTR** :

```bash
sudo sysctl -w net.ipv4.ip_forward=1
echo 'net.ipv4.ip_forward=1' | sudo tee /etc/sysctl.d/99-routage.conf
```

**J'anticipe.** Depuis VM-A, `ping 192.168.20.10` va-t-il fonctionner **avant** l'activation du routage ? Après ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

**Avant : non.** Les paquets arrivent chez RTR, qui, sans routage activé, ne les transmet pas. **Après : oui**, à condition que VM-A et VM-B aient RTR pour passerelle. Le premier `sysctl -w` agit immédiatement ; le fichier dans `sysctl.d` le conserve après redémarrage.

</details>

**4.** Teste depuis **VM-A** :

```bash
ping -c 3 192.168.10.1     # la passerelle
ping -c 3 192.168.20.10    # VM-B, à travers RTR
traceroute -n 192.168.20.10   # (paquet traceroute si absent)
```

| Test | Résultat |
|---|---|
| Ping de la passerelle | |
| Ping de VM-B | |
| Sauts de `traceroute` | |

**Point de contrôle :** `traceroute` montre **deux sauts** : 192.168.10.1 puis 192.168.20.10.

**Je comprends.** Pourquoi les VM sur `intnet` n'ont-elles pas d'accès à Internet ? Comment leur en donner un temporairement pour installer un paquet ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Un réseau interne est **isolé** : aucune de ses cartes n'est reliée au monde extérieur. Pour installer un paquet, on ajoute temporairement une **carte NAT** à la VM concernée (`VBoxManage modifyvm VM-A --nic2 nat`), on installe, puis on la retire.

</details>

## Partie C – Instantanés (≈ 30 min)

**1.** Prends un instantané de **VM-A** à chaud, puis casse volontairement quelque chose :

```bash
VBoxManage snapshot VM-A take "avant-test" --description "etat sain"
# dans VM-A :
sudo rm -f /etc/network/interfaces.d/lab && sudo systemctl restart networking
```

**2.** Constate que le réseau de VM-A est cassé (`ip -br a`), puis restaure :

```bash
VBoxManage controlvm VM-A poweroff
VBoxManage snapshot VM-A restore "avant-test"
VBoxManage startvm VM-A --type headless
```

**J'anticipe.** Après restauration, le fichier supprimé est-il revenu ? Les fichiers créés **après** l'instantané ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Le fichier supprimé **est revenu** (retour à l'état de l'instantané). Les fichiers créés **après** l'instantané ont **disparu** : la restauration efface tout ce qui a été fait depuis. C'est pourquoi un instantané ne remplace pas une sauvegarde.

</details>

**3.** Supprime l'instantané une fois la manipulation terminée :

```bash
VBoxManage snapshot VM-A delete "avant-test"
```

**Je comprends.** Pourquoi ne faut-il pas garder un instantané pendant des mois sur un serveur de production ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

L'instantané enregistre toutes les modifications dans un **fichier de différences** qui **grossit** ; la VM **ralentit** (lecture de la chaîne de différences) et le disque de l'hôte peut **saturer**. De plus, un retour en arrière après plusieurs mois ferait perdre tout le travail intermédiaire.

</details>

**2.** *Cas de dimensionnement.* Une PME veut virtualiser **8 serveurs** : 2 de 4 Go de mémoire, 4 de 2 Go, 2 de 1 Go, soit 8 vCPU au total. L'hôte envisagé a 32 Go de mémoire et 8 cœurs physiques. Réserve 4 Go à l'hôte.

- La mémoire suffit-elle ? Quelle marge reste-t-il ?
- Quel est le risque si l'hôte tombe en panne ?
- Cite deux mesures pour le limiter.

<details markdown="1">
<summary>Éléments de réponse</summary>

Mémoire demandée : 2×4 + 4×2 + 2×1 = **18 Go**. Disponible : 32 − 4 = **28 Go**. Marge : **10 Go**. Les 8 vCPU sur 8 cœurs ne posent pas de problème (pas de sur-allocation).
Risque : l'hôte est un **point unique de défaillance** : les 8 serveurs s'arrêtent ensemble.
Mesures : **sauvegarde des VM** (voir S05) ; **second hôte** avec réplication ou haute disponibilité (voir S12) ; alimentation et disques redondants.

</details>

## Partie A – Git : versionner avant d'automatiser (≈ 35 min)

Sur **CTRL** :

```bash
sudo apt update && sudo apt -y install git ansible
git config --global user.name "Prénom NOM"
git config --global user.email "prenom.nom@exemple.fr"
mkdir -p ~/infra/templates && cd ~/infra
git init
echo "# Configuration de l'infrastructure du TP S08" > README.md
git add README.md && git commit -m "Initialiser le dépôt"
```

**1.** Modifie le `README.md` (ajoute une ligne), puis observe :

```bash
git diff
git commit -am "Décrire le périmètre du dépôt"
git log --oneline
```

**2.** Provoque une erreur et reviens en arrière :

```bash
echo "ligne fautive" >> README.md
git commit -am "Ajout par erreur"
git revert --no-edit HEAD
git log --oneline
cat README.md
```

**J'anticipe.** Après le `git revert`, la ligne fautive a-t-elle disparu de l'**historique** ? du fichier ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Elle a disparu du **fichier**, mais l'**historique** garde les deux commits (l'ajout et son annulation) : `git revert` crée un nouveau commit qui annule le précédent, ce qui préserve la traçabilité. Le journal montre trois ou quatre lignes, dont « Revert "Ajout par erreur" ».

</details>

**Je comprends.** Pourquoi ne jamais enregistrer un mot de passe dans le dépôt, même si on le supprime ensuite ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Git **conserve l'historique** : le mot de passe reste lisible dans les anciens commits. Il faut alors le **changer** (il est compromis), pas seulement le supprimer du fichier.

</details>

## Partie B – Inventaire et premier contact (≈ 25 min)

**1.** Prépare l'accès SSH par clé depuis CTRL vers les cibles :

```bash
ssh-keygen -t ed25519 -N "" -f ~/.ssh/id_ed25519
ssh-copy-id utilisateur@192.168.10.11
ssh-copy-id utilisateur@192.168.10.12
```

**2.** Crée dans `~/infra` les fichiers `ansible.cfg` et `inventaire.ini` :

```text
# ansible.cfg
[defaults]
inventory = inventaire.ini
host_key_checking = False
interpreter_python = auto_silent
```

```text
# inventaire.ini
[web]
web1 ansible_host=192.168.10.11
web2 ansible_host=192.168.10.12

[web:vars]
ansible_user=utilisateur
```

**3.** Teste le contact et une commande :

```bash
ansible web -m ping
ansible web -m command -a "uptime"
ansible-inventory --list | head -20
```

**Point de contrôle :** `ping` répond `"ping": "pong"` pour web1 et web2.

**Je comprends.** Que représente `[web:vars]` ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Des **variables communes** à tout le groupe `web` : ici l'utilisateur de connexion SSH. Les définir une fois évite de les répéter pour chaque machine.

</details>

## Partie C – Écrire et appliquer le playbook (≈ 50 min)

**1.** Crée `templates/index.html.j2` :

```text
<!DOCTYPE html>
<html lang="fr"><head><meta charset="utf-8"><title>{{ inventory_hostname }}</title></head>
<body><h1>Serveur {{ inventory_hostname }}</h1>
<p>Configuré par Ansible ({{ ansible_managed }}).</p></body></html>
```

**2.** Crée `site.yml` :

```yaml
---
- name: Configurer les serveurs web
  hosts: web
  become: true
  vars:
    paquets: [apache2, curl]
  tasks:
    - name: Installer les paquets
      ansible.builtin.apt:
        name: "{{ paquets }}"
        state: present
        update_cache: true
        cache_valid_time: 3600

    - name: Déployer la page d'accueil
      ansible.builtin.template:
        src: index.html.j2
        dest: /var/www/html/index.html
        owner: root
        group: root
        mode: "0644"
      notify: Recharger Apache

    - name: Interdire la connexion SSH de root
      ansible.builtin.lineinfile:
        path: /etc/ssh/sshd_config.d/50-durcissement.conf
        regexp: "^#?PermitRootLogin"
        line: "PermitRootLogin no"
        create: true
        mode: "0644"
      notify: Recharger SSH

    - name: Apache démarré et activé
      ansible.builtin.service:
        name: apache2
        state: started
        enabled: true

  handlers:
    - name: Recharger Apache
      ansible.builtin.service:
        name: apache2
        state: reloaded

    - name: Recharger SSH
      ansible.builtin.service:
        name: ssh
        state: reloaded
```

**3.** Vérifie la syntaxe, simule, puis applique (le mot de passe `sudo` est demandé avec `-K`) :

```bash
ansible-playbook site.yml --syntax-check
ansible-playbook site.yml --check -K
ansible-playbook site.yml -K
```

**4.** Relance **la même commande** :

```bash
ansible-playbook site.yml -K
```

| Exécution | `ok` | `changed` |
|---|---|---|
| 1re application | | |
| 2e application | | |

**J'anticipe.** Que vaudra `changed` à la deuxième application ? Pourquoi ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

`changed=0` : les tâches décrivent un **état** (paquet présent, fichier conforme, service démarré) ; les deux machines étant déjà conformes, rien n'est modifié. C'est l'**idempotence**. À la première exécution, `changed` est supérieur à zéro (paquets installés, fichiers créés, service démarré).

</details>

**5.** Vérifie le résultat depuis CTRL :

```bash
curl -s http://192.168.10.11 ; curl -s http://192.168.10.12
```

**Point de contrôle :** chaque page affiche le nom de **sa** machine (`web1`, `web2`).

**Je comprends.** À quoi sert le `notify` ? Que se passe-t-il à la deuxième exécution ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

`notify` déclenche un **handler** (ici recharger Apache ou SSH) **uniquement si** la tâche a changé quelque chose. À la deuxième exécution, rien ne change, donc **aucun rechargement** : on évite de perturber le service pour rien.

</details>

## Partie D – Provoquer et détecter une dérive (≈ 30 min)

**1.** Sur **web2**, modifie la configuration **à la main** :

```bash
echo "<p>modifié à la main</p>" | sudo tee -a /var/www/html/index.html
sudo sed -i 's/PermitRootLogin no/PermitRootLogin yes/' /etc/ssh/sshd_config.d/50-durcissement.conf
```

**2.** Depuis **CTRL**, détecte la dérive **sans rien modifier** :

```bash
ansible-playbook site.yml --check --diff -K
```

**J'anticipe.** Quelles tâches Ansible va-t-il signaler comme `changed`, et sur quelle machine ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Sur **web2 uniquement** : la page d'accueil (le contenu a changé) et la règle SSH (`PermitRootLogin` n'est plus à `no`). Les tâches de web1 restent `ok`. Avec `--diff`, Ansible montre les lignes en désaccord.

</details>

**3.** Corrige en réappliquant, puis vérifie :

```bash
ansible-playbook site.yml -K
ansible-playbook site.yml -K       # doit revenir à changed=0
```

**Je comprends.** Pourquoi est-il préférable de corriger via le playbook plutôt que de rééditer le fichier à la main sur web2 ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

La correction à la main est **non tracée** et **non reproductible** ; elle recrée de la dérive. Le playbook dans Git garde **qui a changé quoi et pourquoi**, et reproduit le même résultat sur toutes les machines, y compris une machine neuve.

</details>

## Partie E – Enregistrer le travail (≈ 20 min)

```bash
cd ~/infra
printf "*.retry\n" > .gitignore
git add ansible.cfg inventaire.ini site.yml templates .gitignore
git commit -m "Configurer les serveurs web (Apache, page d'accueil, SSH sans root)"
git log --oneline
```

Ajoute ensuite une tâche de ton choix (par exemple installer `vim-tiny` ou créer un utilisateur `audit`), applique, constate `changed`, relance, constate `changed=0`, puis commit avec un message qui explique **pourquoi**.

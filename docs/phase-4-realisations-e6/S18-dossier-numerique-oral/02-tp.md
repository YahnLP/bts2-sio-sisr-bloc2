## Partie B – Analyser trois expressions des besoins (≈ 30 min)

Pour chaque expression, remplis en **10 minutes** la fiche d'analyse (reformulation en une phrase, exigences, ce qui existe déjà, ce qui change, questions à poser, critères de recette).

### Expression 1

| Rubrique | Contenu |
|---|---|
| **Circonstances** | Le site de rendez-vous du Cabinet Delorme ralentit aux heures de pointe. Une réalisation de répartition de charge entre deux serveurs web est en place. |
| **Spécifications fonctionnelles** | Ajouter un troisième serveur web identique, avec ses sondes de santé, et rendre son état visible dans la supervision. |
| **Production attendue** | Trois serveurs servis en alternance ; arrêt d'un serveur sans interruption du service ; alerte à l'arrêt. |
| **Documentation** | Rapport de tests · documentation technique |

### Expression 2

| Rubrique | Contenu |
|---|---|
| **Circonstances** | Une deuxième agence (192.168.30.0/24) rejoint le cabinet. Un tunnel relie déjà le siège à l'agence 1. |
| **Spécifications fonctionnelles** | Relier l'agence 2 au siège avec le même niveau de sécurité, sans interrompre l'agence 1. L'agence 2 ne doit **pas** accéder au réseau de l'agence 1. |
| **Production attendue** | Tunnel opérationnel, filtrage vérifié, plan d'adressage mis à jour. |
| **Documentation** | Documentation technique · rapport de tests |

### Expression 3

| Rubrique | Contenu |
|---|---|
| **Circonstances** | La sauvegarde de cette nuit a échoué : le disque était plein. Personne n'a été prévenu et l'échec a été découvert au matin. |
| **Spécifications fonctionnelles** | Détecter et notifier tout échec de sauvegarde ; vérifier qu'une restauration est possible ; éviter la saturation du disque. |
| **Production attendue** | Alerte fonctionnelle, restauration testée, mesure préventive appliquée. |
| **Documentation** | Rapport d'incident · rapport de tests |

### Fiche d'analyse (à recopier pour chaque expression)

| Question | Réponse |
|---|---|
| Reformulation en une phrase | |
| Exigences (liste) | |
| Ce qui existe déjà (dans la réalisation) | |
| Ce qui change | |
| Impact et risques | |
| Questions à poser à la commission | |
| Critères de recette (mesurables) | |
| Plan en étapes (durées sur 60 min) | |

<details markdown="1">
<summary>Éléments de réponse (expression 3)</summary>

Reformulation : « Détecter et signaler les échecs de sauvegarde, prouver qu'on sait restaurer, et empêcher la saturation du disque. » Exigences : alerte < 5 min après un échec ; restauration testée ; place disque surveillée (avertissement et critique) ; rotation des archives. Existe déjà : script de sauvegarde, supervision, journaux centralisés. Change : alerte sur le code de retour et sur le journal ; seuil d'espace disque ; rotation. Questions : « Quelle perte de données est tolérable ? À qui notifier ? » Critères : un échec simulé déclenche l'alerte ; restauration et `sha256sum` identiques ; l'espace disque reste sous 80 %. Plan (60 min) : 10 min diagnostic et mesure initiale · 20 min alerte · 15 min restauration · 10 min rotation et seuil · 5 min documentation. **Rapport d'incident** à produire : symptôme, cause (disque plein), correction, prévention.

</details>

## Partie C – Rédiger une expression des besoins pour un camarade (≈ 20 min)

La commission écrit l'expression des besoins qui sera donnée au candidat, **à partir de sa fiche** (annexe VII-3). Elle doit être **circonscrite** : faisable en 60 minutes sur la réalisation choisie.

| Rubrique | À rédiger |
|---|---|
| **Réalisation retenue** (R1 ou R2) | |
| **Circonstances** | |
| **Spécifications fonctionnelles** | |
| **Documents fournis** | |
| **Production attendue** | |
| **Documentation à présenter** | rapport de test · documentation technique · rapport d'incident · documentation utilisateur · autre |

**Contrôle de faisabilité** (par un autre membre du trinôme) : cette expression peut-elle être traitée en 45 minutes de réalisation et 10 minutes de recette ? Qu'est-ce qui la rendrait trop longue ou trop courte ?

<details markdown="1">
<summary>Éléments de réponse</summary>

Une bonne expression : **un seul sujet**, un résultat **observable**, des **contraintes chiffrées**, une **production attendue** précise. Trop longue : plusieurs objectifs, ou un élément qui n'existe pas encore dans la réalisation. Trop courte : une modification d'une ligne sans enjeu de conception, de test ou de documentation.

</details>

## Partie D – Version courte de l'épreuve (≈ 90 min)

Chaque candidat passe une **version réduite** de l'épreuve, sur la réalisation de son choix, avec l'expression de la partie C (écrite par son camarade) :

| Étape | Durée | Qui |
|---|---|---|
| Analyse de l'expression des besoins | 15 min | Candidat seul (les autres préparent leurs outils) |
| Entretien 1 (explicitation) | 10 min | Candidat et commission |
| Réalisation | 45 min | Candidat, **dans son environnement** |
| Entretien 2 (recette) | 10 min | Candidat et commission |
| Retours | 10 min | Les trois |

Pendant ce temps, l'**observateur** remplit la grille :

| Critère (grille nationale) | Observations | Niveau |
|---|---|---|
| Identifie et exploite les besoins, contraintes, indicateurs | | |

Niveaux : **Non maîtrisé**, **Maîtrise partielle**, **Bonne maîtrise**, **Excellente maîtrise**, **Non évalué**.
